# 发布、签名与安装

插件有两种分发方式。

**市场上架（推荐）。** 开发者照旧签名打包，把包交给 Hub。Hub 审核通过后给这个版本盖上架证明，放进签过名的索引。xLyra 出厂就认识这枚章，管理员可以在 **设置 → 插件 → 市场** 里浏览、安装和更新，不用再导入开发者公钥。安装仍然走现有的校验、样本自检和权限确认，市场只是省掉找包、传包、导公钥。

**私下分发。** 把 `.xlp` 交给管理员，在 **设置 → 插件 → 已安装** 里手动上传。未签名的包只能走这条路。离线部署和私有插件继续用手动上传，不经过市场。

## 开发者：打包

```bash
xlyra-plugin pack --sign my-key.pem
```

得到 `dist/<id>-<version>.xlp`。每次发布前请提高 `manifest.json` 里的 `version`：同一个 id 同一个版本如果内容不同，会被拒绝。市场上架不收预发布版本号（如 `1.1.0-beta.1`）。

## 上架市场的展示信息

市场卡片上的图标取自包内 manifest 的 `icon`。没有声明时显示名称首字。审核会检查图标在深色底板上是否清楚。规范见[图标](./manifest.md#图标)。

## 签名

签名是可选的，但建议做。进市场则必须签名：开发者签名和 Hub 上架证明缺一不可。签名用 ed25519：

1. `xlyra-plugin keygen --out my-key.pem` 生成密钥，**只做一次**，私钥自己保管。Hub 登记公钥页上的命令也使用这个文件名。
2. 私下分发时，把输出的 `public_key` 发给管理员（或放在你的发布页面上）。市场上架不需要管理员再导入这把公钥。到 Hub 登记时，把 `public_key=` 后面的内容贴进「公钥」，再用同一把 `my-key.pem` 签页面上给出的挑战。
3. 之后每次 `pack --sign my-key.pem`。

签名覆盖包里除 `signature.json` 以外的所有文件。包在签名之后被改动，`verify` 和上传都会失败。

xLyra **不签发开发者证书**。私下分发的信任仍然由管理员决定：只有管理员手动导入的公钥才算「受信」。市场上架的版本凭 Hub 的上架证明显示为「市场审核」。

## 命令行发布到市场

在 Hub 控制台的开发者页创建 API 令牌。明文只显示一次，请放进环境变量，不要写进命令（会留在 shell 历史里）。

```bash
xlyra-plugin keygen --out my-key.pem
xlyra-plugin pack --sign my-key.pem
export XLYRA_HUB_TOKEN='xlh_…'
xlyra-plugin publish dist/<id>-<version>.xlp --changelog "修复额度解析"
```

`publish` 会先做和 `verify` 相同的本地检查，未签名的包会被拒绝。通过后上传到 Hub（默认 `https://xlyra.yachiyo.im`），打印提交编号，并每 3 秒查询状态，直到待审核、已批准、已发布、已退回、检查未通过或已撤回。`--hub` 可以改地址，必须是 https；本机测试可以用 `http://127.0.0.1` 或 `http://localhost`。令牌需要 `publish` 权限，只能提交和查询，不能批准或吊销。

## 管理员：安装

在管理后台的 **设置 → 插件** 页面操作。市场关闭时只保留「已安装」。

### 从市场安装

在「市场」里打开插件，确认它会访问的主机和需要的权限，再安装。服务端下载包、核对哈希、校验开发者签名和上架证明，然后做静态校验和样本自检。通过后可以选择当时启用（主机确认、权限勾选照旧），或只安装、稍后在「已安装」里启用。吊销列表过期时，不能从市场新装，也不能自动升级，直到同步成功。

### 手动上传

#### 1. 导入受信公钥（可选）

在「受信公钥」里添加开发者给你的公钥。添加后，由该密钥签名的包就是「受信」的。

#### 2. 上传

上传 `.xlp`。服务端会做静态校验、加载并运行包内样本，失败会显示原因，且不能启用。通过后状态为已验证。

如果这个包的哈希和市场里某个尚未被安全吊销的版本相同，xLyra 会补上 Hub 的上架证明，信任状态变为「市场审核」，并按市场插件接收更新提示。前提是市场开着，而且本地已经同步到这个版本。

#### 3. 启用

选择某个版本启用：

- **市场审核**或**受信签名**：直接进入主机和权限确认。
- **未签名或签名者不在受信列表里**：需要二次确认，操作会写进审计日志。
- 同一个插件同一时间只有一个版本处于启用状态。启用新版本会让旧版本自动变为停用。

`site_provider` 插件必须使用受信签名或市场审核，管理员启用时需要确认 manifest 声明的主机列表（每次启用都要确认）。

手动上传的包如果只是签名者公钥被 Hub 吊销，信任状态旁会标「签名者已被 Hub 吊销」，插件不会因此被停用。哈希和市场里被安全吊销的版本相同时，会按吊销规则停用。

### 4. 让它生效

启用只是让 xLyra 加载插件；插件真正用在哪里，取决于类型：

| 类型 | 做法 |
| --- | --- |
| `quota_probe` | 在插件的「版本」弹窗里，从「站点」下拉框选择站点（可多选），点弹窗底部的「应用」。这些站点的额度刷新改用它。站点编辑页的「额度探测」下拉框不会出现第三方插件 |
| `protocol` | 分配一个标识（slug），对外路径是 `POST /v1/plugins/<slug>` |
| `model_list`、`credential_check`、`error_classifier` | 同上：在下拉框里选择要使用它的站点（可多选），点「应用」；从下拉框里取消某个站点再应用，就解除它的绑定、回到默认行为 |
| `pricing_parse` | 选择站点后，对每个新选的站点先点「预览价格」，核对结果并勾选确认，再点「应用」 |
| `site_detect`、`model_metadata` | 不需要绑定，启用即对所有站点生效 |
| `site_provider` | 不需要绑定，也不能绑定到单个站点。受信签名或市场审核并确认主机后，按声明的站点类型出现在创建页。`api_key` 与 `account_pool` 都是这样。详见[站点类型](./site-provider.md) |

**绑定是可选的。** 上面需要绑定的类型，不绑定时只是被加载，不会用于任何站点；绑定只决定它在哪些站点生效。同一个站点同一种类型同一时间只能绑定一个插件，重新绑定会替换。插件被停用或卸载后，对应的绑定自动失效，站点回到默认行为。

### 5. 试跑

「试跑」会在服务端用包内样本重新跑一遍，结果直接显示在该版本那一行：是否通过，以及耗时（精确到微秒，样本通常不到 1 毫秒）。它不会向真实站点发请求。关闭弹窗后结果不保留。

## 更新策略

每个市场来源的插件可以单独设置更新策略。默认是**仅提示**。

| 策略 | 行为 |
| --- | --- |
| 关闭 | 不提示，不升级 |
| 仅提示 | 已安装列表和市场里标出可更新的版本，并写一条管理员审计 |
| 自动 | 同时满足下面的安全升级条件时自动升级；有一条不满足就退回「仅提示」，并写明是哪一条 |

另有全局开关「允许自动更新」。关掉之后，策略为「自动」的插件也只提示。

自动升级全部满足才执行：

1. 与当前 xLyra 兼容。
2. 开发者指纹与当前启用版本相同。
3. 类型不变。
4. 主机和权限没有新增。
5. 主版本号不变（`1.x` 可以到 `1.y`，不能到 `2.0`）。
6. `site_provider` 的站点类型 ID 不变。
7. 不是被吊销的版本，而且本地吊销列表没有过期。
8. 不是 `pricing_parse`。这类插件决定价格，升级也要先预览再确认，只能手动。

自动升级复用启用流程：新版本先在后台加载并做样本自检，通过才切换，失败则保持旧版本。站点绑定和协议 slug 会跟着切到新版本。审计里的操作者是 `system:auto-update`。

手动更新走和市场安装相同的确认：下载校验之后，仍然要确认主机和权限。

## 升级、回滚与卸载

| 操作 | 做法 |
| --- | --- |
| 升级 | 市场里点「更新」，或上传新版本后启用 |
| 回滚 | 重新启用旧版本 |
| 停用 | 停用当前启用的版本 |
| 卸载某个版本 | 在插件的「配置」弹窗里，只能删除未启用的版本；启用中的版本要先停用 |
| 卸载整个插件 | 插件已停用（没有启用的版本）时，插件列表里会出现「卸载」，会删除它的全部版本，以及它的绑定、待处理事件和操作记录 |

启用新版本时，新版本会先在后台完成加载和样本自检，通过后才切换，正在处理的请求不受影响。新版本加载失败则不切换，当前版本继续运行。

升级 `site_provider` 时，如果已有站点使用当前的站点类型 ID，新版本不能改这个 ID，启用会被拒绝（`js_plugin_site_type_locked`）。

停用后，该类型的站点仍保留数据，但不再参与路由，也不出现在下游模型目录。仍有站点在用时，不能卸载整个插件，也不能删除最后一个版本（`js_plugin_in_use`），需要先删除这些站点。

## 自动回退与吊销

运行异常的插件会被自动停用，规则见[限制与安全](./limits-and-security.md#自动保护熔断)。手动升级或手动上传的版本停用后不会自动回到旧版本。

**自动升级**上来的版本如果在升级后 24 小时内触发熔断，xLyra 会重新启用升级前的版本，把新版本标成「自动回退」，并暂停这个插件的自动更新，直到管理员改更新策略或另行处理。

安全吊销（市场来源，或手动上传但包哈希相同）会停用该版本，不受更新策略影响。条目里有 `rollbackTo` 时，才会尝试启用那个版本：本地没有就从市场下载并照常校验，而且必须是同一个开发者、不能新增主机和权限，否则只停用。没有 `rollbackTo` 时不自动启用任何版本。

弃用只显示提示。吊销开发者公钥不会停用已经审核过的市场版本。

## 插件存在哪里

上传的插件包保存在 xLyra 的 PostgreSQL 数据库里（`js_plugin_versions` 表，包本身是一个二进制字段，旁边是清单、哈希、签名者、状态、自检结果和已授予的权限），受信公钥在 `js_plugin_trusted_keys` 表，绑定、事件队列和操作记录也在同一个库的 `js_plugin_*` 表里。不会写到文件系统，xLyra 数据目录（`/data`）里没有插件文件。

所以插件是否持久化，取决于数据库的数据目录是否持久化：用官方的 `docker-compose.yml` 时，它由 `./postgres:/var/lib/postgresql/data` 挂载保存。备份数据库就备份了所有已上传的插件。服务启动和启用版本时，xLyra 会从数据库把已启用的包读出来，在内存里编译运行。内置插件则直接编译在程序里。

多实例部署时，启用、停用、删除和协议路径变更会在数秒内同步到所有实例，无需重启。市场同步和自动升级只在拿到同步租约的那一个实例上执行。

## 审计

上传、启用、停用、卸载、绑定、试跑、导入或移除公钥、从市场安装、更改更新策略，都会记入管理员审计日志。自动升级、自动回退和吊销由系统写入审计，包含插件 id、版本和包摘要。

## 内置插件

xLyra 自带的内置插件（`xlyra.` 开头）只读展示，无法停用或卸载，它们也是你编写插件时的最佳参考。
